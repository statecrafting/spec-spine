# 074: Shipped is not the same as working

## 1. Purpose

Close eleven ways the tool ships something an adopter cannot use, and add the
one refusal that would have caught the worst of them.

On 2026-09-08 two adopters installed or upgraded the governed loop. Neither
was looking for defects in spec-spine; both found them within a session:

- one wrote `crates/**` into `extra_hashed_inputs`, measured no effect, and
  concluded the key was inert;
- the other found `standards/**` and `.github/workflows/**` already in their
  config, inherited from a scaffold, and confirmed those patterns "had never
  contributed to any content hash."

In the `glob` crate `dir/**` enumerates directories and the hasher keeps only
files, so both patterns match nothing. That is spec 069's subject, and 069
fixed the **default**. It could not fix a value already written into an
adopter's `spec-spine.toml`, and `scaffold.rs` writes exactly that value into
every repository it initializes. So the pre-069 cohort carries the broken
literal in a committed file, upgrades the binary, sees no restale, and
reasonably concludes it was never affected. Spec 069 section 4 named the lint
that catches this and deferred it. Two adopters in one day is the evidence for
building it.

The other findings share one shape. `init --with-kit` writes
`.githooks/enable-merge-driver.sh` at mode 644, and its own documentation says
to run it as `./.githooks/enable-merge-driver.sh`. It writes no binding for the
merge driver those hooks register. It writes `scripts/verify-spec.sh`, which
spec 049 replaced with `spec-spine verify`. Run in a repository that already
has a `000` spec it writes a second one, reports "0 skipped", and leaves a
corpus its own compiler refuses with `V-004`. `AGENTS.md` says to ask
`spec-spine --version` "before believing any exit code" and its step list never
asks. The `/init` skill beside it still prescribes reading clap's English from
stderr, the ritual that same document retired as unreliable.

None of these is subtle, and all of them shipped. The reason is the one spec
071 named when a substring assertion let an over-broad push gate reach every
adopter: **the acceptance asserted that a thing exists, not that it works.**
A test that a file is written passes on a file nobody can execute. A test that
a key is emitted passes on a key that matches nothing.

**This spec `amends` 065.** Its section 3.2 decided that
`kit/.gitattributes-stanza` "is a block to append to an existing file rather
than a file to write", and excluded it from what `--with-kit` writes. Section
3.3 below requires the binding to be written, which changes that decision. Per
spec 040 the edge is declared here only; 065's `spec.md` is not edited.

**No `amends` on 057, checked rather than assumed.** Section 3.2 below changes
the `L-008` message, and 057 quotes that message. But 057 also states, in the
same section, that "the message MUST name both remedies, because they are
genuinely different choices", and then spells out the cost of each: a glob
"folds the file into the global scalar, which restamps every shard when it
changes: correct for a small set of governance files, wrong for a large tree of
source." The shipped string names the remedies and drops the reasoning. The
spec is already right and the implementation under-delivers, so this is
conformance, not amendment.

**No `amends` on 069.** Section 3.9 requires the migration note to cover the
cohort whose config carries the broken literal. Spec 069 section 3.5 requires
the note to address the adopter who did not override the key. It is silent
about the other cohort rather than denying it exists, and silence is not
contradiction: 3.9 adds substance to a note 069 mandated rather than changing
what it must say.

## 3. Behavior

### 3.1 A hashed-input pattern that can match no file is refused

The lint MUST emit a new diagnostic, `L-010`, for any `[index]
extra_hashed_inputs` entry whose pattern ends in `/**`. Such a pattern
enumerates directories, and the hasher keeps only entries that are files, so it
can never contribute a byte to any content hash whatever the tree contains.

The message MUST name the working form (`dir/**/*`), because the entire cost of
this defect is that the broken form looks correct.

`L-010` MUST be a **warning**, so `lint --fail-on-warn` refuses it. Unlike
`L-008`, which flags a state a corpus may hold deliberately, a pattern that can
match nothing under any tree is never intentional: an adopter who wants to
match nothing writes no entry.

The check is on the **pattern**, not on whether it currently matches. A pattern
that matches nothing today may be a legitimate forward-looking entry, which is
the false-positive spec 069 section 4 worried about when it deferred this. That
worry is answered by narrowing the rule to the one form that is unconditionally
inert rather than to the symptom.

### 3.2 The `L-008` message explains the choice it offers (conformance with 057)

The `L-008` message MUST carry the reasoning spec 057 requires and the shipped
string omits: that a glob in `extra_hashed_inputs` folds the file into the
**global** scalar and therefore restamps every shard when it changes, correct
for a handful of governance files and wrong for a tree of source; and that a
`section` or `symbol` unit is hashed through its span and stales only the
claiming spec's shard.

The message MAY carry it by reference to a documentation anchor rather than
inline, since a diagnostic emitted once per claimed path must stay readable at
a hundred repetitions. What it MUST NOT do is offer two remedies as though they
were interchangeable, which is what it does today and what sent an adopter to
the wrong one.

### 3.3 `--with-kit` writes the binding for the driver it installs (amends 065)

`spec-spine init --with-kit` MUST write, or append, the `.gitattributes` stanza
that binds the committed shard globs to the `spec-spine-derived-regen` merge
driver, in the same run that writes `.githooks/enable-merge-driver.sh` and
`.githooks/merge-derived-index.sh`.

Appending MUST be idempotent: a second run MUST NOT duplicate the stanza, and
an existing `.gitattributes` MUST be preserved. This is the reason 065 excluded
it, and it is a solvable problem rather than a reason to ship a driver that
cannot fire.

The driver remains opt-in per clone, which 065 and spec 020 both require:
writing the binding does not register the driver, and `enable-merge-driver.sh`
is still what does that.

### 3.4 A scaffolded executable arrives executable

`ScaffoldFile` MUST carry whether a file is executable, and the CLI MUST apply
it when writing. Today the struct is `{ rel_path, contents, overwrite }` and
every file lands at 644, including two shell scripts whose own documentation
invokes them by path.

The flag MUST be set for every `.sh` the scaffold writes. On a platform with no
executable bit the field is inert, and the scaffold stays a pure function of
`(Config, with_kit)` because the bit is data in the returned `Scaffold`, not an
IO decision taken by the writer.

### 3.5 `init` does not create a corpus its own compiler refuses

`init` MUST NOT write a bootstrap spec at an ordinal already used by a spec in
the target repository. It MUST skip it and say so, in the same voice as every
other skipped file, rather than writing a second `000`.

Today it writes `specs/000-bootstrap` beside an existing `specs/000-*` and
reports "11 file(s) written, 0 skipped", and the next `compile` refuses with
`V-004 numeric prefix '000' is shared by ...`. The refusal is correct and loud,
which is why this is a nuisance rather than a corruption; a tool that knowingly
produces a state its own validator rejects is still a tool to fix.

The check is on the **ordinal**, not the directory name, because the collision
`V-004` reports is on the ordinal.

### 3.6 The kit stops shipping what the tool absorbed

`kit/scripts/verify-spec.sh` MUST be removed. Spec 049 absorbed it into
`spec-spine verify`, which is the verb the kit's own skills now call, and the
audit that requested it recorded that three adopters had each written the same
script. Shipping it afterwards hands a fourth copy to every new adopter.

Any kit file that documents it MUST be updated in the same change, so the
removal does not leave a dangling instruction.

### 3.7 The protocol schedules the read it calls a precondition

`AGENTS.md`'s New Sessions step 1 MUST include `spec-spine --version` in its
parallel batch, and step 2 MUST consult it before reporting any freshness
verdict. The document already states that the version must be known "before
believing any exit code" and never schedules the read, so the precondition
holds only for an agent that reads the prose below the step list.

The `2 (stale)` row of the exit-code table MUST point at the version check
rather than at stderr.

The `/init` skill MUST drop its stderr rule. It currently tells a session to
read `unexpected argument` from stderr, which is the ritual `AGENTS.md` retired
for being pinned to a dependency's message format. The skill MUST carry the
generic precondition only, and leave exit-code semantics to `AGENTS.md`, which
is where the skill already says the project layer lives.

The rule is retired because it is brittle, not because spec 063 changed its
outcome. A post-063 binary never reaches that path, since `--check` parses;
only a pre-063 binary does, and there clap genuinely did spend exit 2 on it.
Stating the reason correctly matters, because the replacement is a version
read and not an exit-code correction.

### 3.8 This repository pins itself

`spec-spine.toml` MUST set `[meta] required_version` to a requirement matching
this repository's own package version. Spec 062 built the key for exactly the
failure a dogfooding repository is most exposed to, an in-tree binary that
predates the checkout, and this repository does not use it.

`Config` derives `#[serde(deny_unknown_fields)]`, so a binary predating 062
fails to deserialize the key and exits **3** with a config error, never 2. The
signal is therefore unambiguous in both directions, and section 3.7's manual
version read can be documented as the portable fallback for a repository that
has not set the key rather than as the standing procedure here.

### 3.9 The migration note reaches the cohort that cannot be fixed by upgrading

`docs/adoption-guide.md` MUST tell an adopter whose `spec-spine.toml` contains
`standards/**` or `.github/workflows/**` that those entries match no files,
that upgrading does not change them because the value is theirs and not the
default, and that the fix is to rewrite them as `dir/**/*` and re-index once.

Spec 069's note addresses the adopter who relies on the default. This cohort is
in the opposite position and the more dangerous one: their upgrade produces no
restale at all, which reads as confirmation that they were unaffected. The note
MUST say that explicitly rather than leaving the absence of a restale to be
interpreted.

Every adopter scaffolded before v0.16.0 is in this cohort, because
`scaffold.rs` emits the default's value into the file.

### 3.10 The guards run what was written

Each of 3.3 to 3.6 MUST be asserted by exercising the artifact, not by
inspecting the scaffold's data:

- the scaffolded `.sh` files MUST be asserted **executable on disk** after a
  real `init --with-kit` into a temporary repository;
- the `.gitattributes` binding MUST be asserted present, and asserted **not
  duplicated** after a second run;
- the ordinal guard MUST be asserted by running `init` into a repository that
  already has a `000` spec and then running `compile`, which MUST pass;
- `L-010` MUST be asserted by a config carrying `dir/**`, and MUST NOT fire on
  `dir/**/*`.

This section is the spec's own argument applied to itself. Every defect it
fixes was already covered by a test that asserted the artifact existed.

## 4. Out of scope

**Renaming the `/init` skill.** The kit's `/init` shadows Claude Code's
built-in `/init` and inverts its semantics: the built-in is a one-time,
repository-level, writing operation and the kit's is a per-session read-only
one. That is a real defect and it is a rename with an adopter migration
touching every `AGENTS.md`, which does not belong in a change whose other
eleven parts are defects with no migration at all. It is its own spec.

**The CLI's own naming asymmetries.** `compile --check` is a flag where `index
check` is a subcommand, and `attest` / `verify-attestation` are two top-level
verbs where every other noun groups its operations. Both are real and both need
a deprecation window, which is the same spec as the rename and not this one.

**Generalising `L-010` to every glob-shaped config key.** `[index.slices]`
entries and `[coupling] bypass_prefixes` also take patterns, and `dir/**` may
be legitimate in a slice meant to match nothing yet. Spec 069 section 4 raised
that exact false positive. This spec narrows to `extra_hashed_inputs`, where a
pattern that matches no file has no legitimate reading.

**Folding claimed `file` units into the ledger.** Spec 057 section 4 left it
open and this spec does not reopen it. `L-010` reduces how often an adopter
reaches for the wrong remedy; it does not change what a `file` unit means.

**Auditing installed adopters.** Nothing here retrofits a harness already
copied. Section 3.9 is the only instrument that reaches them, which is why it
is a documentation requirement rather than a code one.

## 5. Resolved decisions

**2026-09-08: `L-010` refuses the pattern form, not the empty match.** The
tempting rule is "warn on any entry matching zero files", which catches more.
It also fires on a forward-looking entry in a specify-first corpus, which is
the false positive spec 069 section 4 named when it deferred this lint. A
pattern ending `/**` is inert under **every** tree, so refusing the form is
decidable from the config alone and has no legitimate counter-example. The
narrower rule is the one that can ship.

**2026-09-08: `amends` 065, but not 057 or 069.** All three specs are touched
and only one has a requirement contradicted. 065 decided the stanza is not
written; 3.3 writes it. 057 already requires the reasoning that 3.2 adds, so
that is conformance. 069 is silent about the second cohort rather than denying
it, so 3.9 adds to its note. Working this out by reading each spec's words is
the rule 071 section 5 set, and it is worth recording that it produced three
different answers on one change.

**2026-09-08: the ordinal guard skips rather than refuses.** `init` could exit
non-zero on an existing `000`. It should not: `init` is additive by design and
already reports skipped files, and a repository with a bootstrap spec that runs
`init --with-kit` for the harness is doing something legitimate. Skipping with
a message fits the verb's existing contract; refusing would make the kit
uninstallable in exactly the repositories most likely to want it.

**2026-09-08: eleven findings, one spec, because they share an argument.** They
were considered as three specs, split by mechanism. They are one claim: the
acceptance asserted existence rather than function, and section 3.10 is that
claim made testable. Splitting them would produce three specs each restating
the same reason, and would leave no home for the section that fixes it.
