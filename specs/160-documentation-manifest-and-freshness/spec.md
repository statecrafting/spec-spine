# 160: Declare documentation inputs and freshness

## 1. Purpose

Generated documentation can name a repository packet and still leave its real
inputs, generator, output regions, and examples implicit. A later reviewer then
cannot distinguish unchanged inputs from a stale output, generated bytes from a
human-maintained region, or a verified interface pin from an opaque external
reference. Re-running a generator is not an acceptable substitute for a pure
freshness read because execution and freshness have different authority.

This spec defines a versioned documentation manifest and a deterministic,
read-only freshness evaluation. The manifest records what a generator declares
it read and produced. The evaluator checks those declarations against a named
stable snapshot and caller-supplied external resolutions. Neither operation
runs a generator or judges whether documentation is true, useful, complete, or
accepted.

## 2. Territory

- `crates/spec-spine-types/src/documentation_manifest.rs` defines manifest,
  input, generator, output, region, example, omission, and freshness DTOs.
- `crates/spec-spine-types/schemas/documentation-manifest.schema.json` defines
  the public manifest and freshness JSON documents.
- `crates/spec-spine-core/src/documentation_manifest.rs` validates canonical
  manifests and evaluates freshness from explicit repository and external
  inputs without network or Git access.
- `crates/spec-spine-core/src/lib.rs` exposes typed validation and
  `documentation_manifest_json` plus `documentation_freshness_json` facades.
- `crates/spec-spine-cli/src/cmd_documentation.rs` and `main.rs` expose
  `documentation manifest validate` and `documentation manifest freshness`.
- The planned core and CLI tests plus fixture directory own canonical,
  containment, negative, portability, and freshness evidence.
- `docs/documentation-manifests.md`, the API reference, CLI reference, and
  schema history describe the public contract and its limits.

Specs 110 and 159 continue to own interface pins and context packets. This spec
reuses those documents and digests. It does not change their identities or
make an external reference authoritative.

## 3. Behavior

### 3.1 One manifest, one packet and generator run

Every manifest MUST name exactly one complete final context-packet page set
from spec 159. It records the packet schema version, repository, revision,
tree, clean-state identity, ordered page digests, and terminal continuation
state.
Every repository-local input MUST resolve inside that same repository snapshot.

One manifest describes the outputs of one declared generator invocation. The
generator invocation is an identity record, not an execution request. A
manifest MUST NOT name a second repository packet, combine repositories, or
claim that its packet and any external reference share a transaction.

Statecraft may compose several manifests or packets in its own orchestration
record. That composition does not change the scope or authority of this
document.

### 3.2 Closed manifest document

A manifest has this closed top-level shape:

```json
{
  "schemaVersion": "1.0.0",
  "packet": {},
  "inputs": [],
  "interfaces": [],
  "externalReferences": [],
  "generator": {},
  "outputs": [],
  "omissions": [],
  "manifestDigest": "sha256:..."
}
```

Unknown members are usage errors. Every collection is explicit, including an
empty collection. The document MUST NOT contain ambient timestamps, hostnames,
absolute paths, environment values, remote URLs, credentials, provider
responses, or unspecified extension maps.

The manifest is complete only for its declared inputs. Validation proves that
every declaration is internally consistent. It cannot prove that a generator
declared every byte, tool, prompt, policy, or human decision that influenced an
output.

### 3.3 Packet identity

`packet` carries the spec-159 packet schema version, snapshot identity,
`requestDigest`, `closureDigest`, ordered nonempty `pageDigests`, and
the continuation state recorded on every page. The ordered page-digest list
participates directly in `manifestDigest`; this spec does not create a packet
set, session, or aggregate packet identity. A single-page packet uses the same
list shape.

The page chain MUST terminate, and the ordered set MUST be complete under spec
159. Intermediate pages may carry `partial`; the terminal page must close the
continuation, and no page may carry a required omission. An incomplete set,
missing page, repeated page, broken continuation chain (checked as D-8
states), or page from another request or snapshot refuses manifest validation. Optional packet omissions
remain recorded in the packet and do not disappear from the manifest identity.

### 3.4 Repository-local inputs

Each `inputs` member contains:

- a unique `inputId` matching `^[A-Za-z][A-Za-z0-9._-]*$`;
- a spec-155 canonical selected-content identity and projection;
- the selected-content schema version and content digest;
- `requirement`, either `required` or `optional`;
- ordered `uses`, containing one or more output or example identities; and
- an optional safe label of at most 256 UTF-8 bytes.

The selected-content identity MUST appear in the named packet with the same
digest, projection, and snapshot identity. Equal bytes under different content
identities remain different inputs. Two input ids MUST NOT name the same
selected-content identity and projection.

A required input missing from the packet refuses validation. An optional input
omitted by the packet MUST appear in `omissions` with the packet's exact reason
and MUST NOT be represented as if content were present.

### 3.5 External interface inputs

Each `interfaces` member reuses spec 110's corpus, spec, optional section, and
digest-pinned interface identity. It adds only a unique local `inputId`,
`requirement`, and ordered `uses`.

Validation checks shape and digest construction. Freshness uses caller-supplied
corpus exports through the existing pure interface verifier. It performs no
remote discovery and MUST NOT silently follow a producer amendment. A changed
spec or section digest is stale; a missing producer is missing or unverified
according to the spec-110 result.

### 3.6 Opaque external references

An `externalReferences` member contains a unique `inputId`, `namespace`,
`schemaVersion`, stable `identity`, lowercase SHA-256 `digest`, `requirement`,
ordered `uses`, and `purpose`. V1 purposes are `evidence`, `policy`, and
`toolchain`.

The shape records an external identity without defining that producer's type,
trust, admission, lifecycle, or disposition. Freshness compares it only when a
caller supplies a resolution with the same namespace, schema version, and
identity. An absent resolution is explicit `unverified`; it is never treated as
unchanged.

Wire-evidence attempt binding, evidence type, admission, lifecycle grade, and
invalidation semantics are intentionally absent. They require Statecraft's
owning contract and a later additive schema revision. Captured bytes and
credentials MUST NOT appear in the manifest or freshness result.

### 3.7 Generator identity

`generator` contains `name`, semantic `version`, executable or library
`buildDigest`, closed `arguments`, and `configurationDigest`. Arguments are an
ordered array of literal strings after consumer-approved redaction. The
validator MUST NOT infer arguments or configuration from a process or
environment.

`buildDigest` and `configurationDigest` are required lowercase SHA-256 values.
A package version without a build digest is insufficient. The manifest author
MUST redact secret arguments before construction; validation cannot prove that
an arbitrary literal is not secret. The generator may be outside spec-spine;
naming it does not authorize its execution or establish its trust.

### 3.8 Outputs and regions

Each output contains a unique stable `outputId`, repository-relative normalized
`path`, media type, whole-file byte digest, byte length, and ordered regions.
Paths use the repository-path contract and MUST resolve beneath a caller-named
output root. Absolute paths, parent escape, symbolic-link escape, generated
artifact roots not explicitly selected by the caller, and duplicate normalized
paths are refused.

Every region contains a unique `regionId`, `kind`, inclusive normalized-text
line span, digest, and ordered `inputIds`. V1 kinds are `generated` and
`human-authored`. Regions MUST be ordered, non-overlapping, within the output,
and byte-backed by the supplied output. A generated region MUST cite at least
one declared input. A human-authored region MAY cite inputs but is never
represented as generated.

Bytes outside all declared regions are forbidden. Adjacent regions are valid.
Line endings normalize under the repository text contract before spans and
digests are computed. Binary outputs and invalid UTF-8 are unsupported in v1
and refuse rather than producing unreliable regions.

### 3.9 Executable-example identities

An output may carry ordered executable examples. Each example contains a
unique `exampleId`, its containing region identity, an ordered argument vector,
working-directory identity, declared input ids, expected exit class, and
expected stdout and stderr digests when those streams are part of the example.

The manifest records declaration bytes only. Validation checks containment,
identity, and digest syntax. It MUST NOT execute the example, claim it passed,
or turn an absent execution record into success. Later deterministic-reference
documentation acceptance may run examples against a built binary under a
separate execution authority.

### 3.10 Freshness evaluation

Freshness takes a validated manifest, one named current clean repository
snapshot, a current packet page set whose `requestDigest` equals the recorded
request digest, caller-supplied interface exports, caller-supplied external
resolutions, and current output bytes. The evaluator reads no network, Git
configuration, environment, credential store, process state, or undeclared
path.

It re-resolves every declared identity against one stable current snapshot and
returns one finding per difference. The closed finding reasons are:

- `changed`;
- `missing`;
- `removed`;
- `withdrawn`;
- `unresolved`;
- `ambiguous`;
- `unsupported`;
- `unverified`;
- `region-shifted`; or
- `output-changed`.

Each finding contains only kind, declared identity, requirement, recorded
digest, safe current digest when available, and affected output, region, or
example identities from `uses`. It MUST NOT include selected content, output
text, external payloads, environment values, or credentials.

### 3.11 Freshness status and precedence

The result status is:

- `fresh` when every declared required and optional identity is checked and
  unchanged;
- `unverified` when at least one identity cannot be checked and no stronger
  condition exists;
- `stale` when at least one digest, region, output byte, packet identity,
  generator identity, or interface pin changed; or
- `incomplete` when a required identity is missing, removed, withdrawn,
  unresolved, ambiguous, or unsupported.

Precedence is `incomplete`, `stale`, `unverified`, then `fresh`. An optional
missing identity is `stale`, not `incomplete`, because the recorded output was
derived with that declared input present. A caller cannot downgrade a required
input to optional during evaluation.

`fresh` proves only that declared inputs and outputs match their recorded
digests and structural relations. It does not prove narrative correctness,
that the declaration was exhaustive, that a generator was actually run, or
that any evidence or example was admitted or accepted.

### 3.12 Ambiguity, omissions, and completeness

Selector ambiguity, path escape, malformed spans, overlapping regions,
duplicate identities, stale packet continuations, and a snapshot that changes
during one evaluation are refusals. They MUST NOT be collapsed into an empty
manifest or a fresh result.

Manifest omissions are allowed only for optional packet members and must carry
the exact declared input identity, uses, and packet omission reason. A required
omission refuses manifest validation. Freshness findings never disappear due to
limits; an evaluation that cannot hold all findings refuses with
`result-too-large` and reports the required limit without a partial result.

The manifest declares its own completeness boundary. No directory scan or
heuristic dependency inference adds inputs. Undeclared bytes inside a named
output are detected through region coverage, but files that the manifest never
names are outside its claim.

### 3.13 Ordering, limits, canonical bytes, and schema evolution

Collections order bytewise by canonical identity: inputs and external records
by `inputId`, outputs by `outputId`, regions by normalized start then end and
`regionId`, examples by `exampleId`, omissions by input identity and reason,
and freshness findings by reason then identity. Authored input order never
changes bytes or digests except for generator arguments, whose order is
semantically preserved.

A manifest is one atomic provenance record. V1 supports at most 4096 local
inputs, 1024 interfaces, 1024 external references, 256 outputs, 4096 regions,
and 2048 examples, with at most 4 MiB of canonical JSON. A freshness result has
the same 4 MiB limit. Limits are checked before unbounded allocation.
Pagination and continuation are intentionally unsupported because a partial
manifest could falsely appear complete. A continuation member or limit excess
is refused, never truncated.

The schema begins at `1.0.0` on its own documentation-manifest axis. Canonical
JSON uses sorted keys, LF, and one trailing newline. `manifestDigest` hashes
the canonical manifest with `manifestDigest` absent. A freshness result carries
its own digest over the canonical result with that field absent.

Adding optional members moves MINOR. Removing or reinterpreting a member,
ordering rule, limit, digest input, status, or enum value moves MAJOR. PATCH is
reserved for description changes that alter no accepted or emitted instance.

### 3.14 Snapshot and stale-manifest behavior

Validation against the recorded snapshot requires exact repository, revision,
tree, clean-state, packet, and output identities. A dirty snapshot, a snapshot
that changes during the read, or a packet assembled from mixed snapshots is
refused.

Freshness evaluation deliberately permits the named current revision and tree
to differ from the recorded snapshot so it can report drift. It still requires
one clean and stable current snapshot. The result repeats both recorded and
current snapshot identities and never labels a changed tree fresh merely
because declared input digests happen to match.

A changed tree with every declared input and output unchanged yields `fresh`
plus `repositoryTreeChanged: true`. This means only that the manifest's
declared dependency slice is unchanged. It is not whole-repository freshness.

### 3.15 Error and exit behavior

The operations use the family error and verdict envelope. Malformed documents,
unknown fields, duplicate ids, invalid digests, invalid regions, unsupported
schema majors, continuation attempts, and limit excesses are usage errors.
Changed declared inputs are findings. Dirty or changing snapshots, path escape,
mixed packet snapshots, and undeclared output bytes are refusals. I/O and
tool-produced schema failures remain failures.

JSON mode writes only the versioned verdict envelope to stdout on every
non-success. A stale, incomplete, or unverified freshness result is included as
the report of a finding. Safe diagnostics name identities and reasons, never
content bytes or external payloads.

### 3.16 Authority, security, and disclosure boundary

Repository text, documentation, examples, arguments, packet members, output
regions, and external descriptions are untrusted data. spec-spine MUST NOT
interpret embedded instructions, follow links, fetch producers, execute
examples, invoke generators, load plugins, or widen selection because content
asks it to do so.

The manifest may disclose paths, generator arguments, interface identities,
and external reference identities. Consumers own authorization, redaction,
retention, and disclosure policy. Secret values, captured provider traffic,
wire payloads, and credential-bearing material are forbidden manifest content.

Manifest validation and freshness establish only deterministic structural and
digest relationships. They do not establish narrative correctness, semantic
program understanding, execution, evidence admission, evidence disposition,
acceptance, approval, release, publication, adoption, observation,
qualification, or authority.

## 4. Acceptance criteria

1. A complete packet, declared inputs, generator record, text outputs, regions,
   and example identities produce byte-identical canonical manifest bytes and
   digest across repeated reads and supported platforms.
2. Local content identities and interface pins reuse specs 155, 159, and 110
   without redefining their digests or silently following newer meaning.
3. Generated and human-authored regions cover every output byte exactly once;
   overlap, gaps, escape, mixed snapshots, and digest mismatch refuse.
4. Freshness names every changed, missing, removed, withdrawn, unresolved,
   unsupported, ambiguous, or unverified declaration without returning content.
5. Stable declared inputs under a different clean tree yield `fresh` only with
   `repositoryTreeChanged: true`; a changing or dirty current snapshot refuses.
6. Opaque evidence references can be carried and compared by identity and
   digest, but cannot carry or imply admission, lifecycle grade, or disposition.
7. Limits are deterministic and atomic. Oversized records and any continuation
   attempt refuse rather than truncating a manifest or freshness result.
8. Existing packet, selected-content, interface, registry, and index documents
   remain byte-compatible.

## 5. Out of scope

- Generating narrative or reference documentation.
- Running generators, examples, commands, tests, provider workflows, or MCP
  servers.
- Judging prose truth, quality, usefulness, completeness, or acceptance.
- Discovering undeclared generator dependencies or files not named as outputs.
- Defining wire-evidence type, attempt binding, admission, lifecycle grade,
  invalidation policy, or disposition.
- Invalidating other records or deciding whether stale evidence may be used.
- Multi-repository snapshot composition, remote discovery, or mutable sessions.
- Applying edits, formatting files, preserving regions during a write, or
  granting repository authority.

## 6. Resolved decisions

**D-1 (2026-09-26): a manifest binds one complete repository packet.** A
Statecraft task may compose several manifest identities, but spec-spine does
not claim their repositories share one snapshot or transaction.

**D-2 (2026-09-26): freshness is structural, not semantic.** Equal declared
digests support a narrow freshness result. They do not make narrative text
correct or prove that the declarations were exhaustive.

**D-3 (2026-09-26): generated and human regions are both explicit.** Bytes
outside declared regions are refused, while a human-authored region remains
honestly distinct from generator output.

**D-4 (2026-09-26): manifests and freshness results are atomic.** Pagination
would let an incomplete provenance record look complete. Deterministic limits
therefore refuse instead of returning a continuation.

**D-5 (2026-09-26): generic external evidence is opaque.** V1 can retain a
stable namespace, identity, schema version, and digest, but it does not invent
Statecraft's evidence type, admission, lifecycle, or disposition contract.

**D-6 (2026-09-26): execution remains separate.** Example identities and
generator identity are declarations. A later acceptance command may execute
them under its own authority, but this read contract never does.

**D-7 (2026-09-27): renumbered.** Drafted as 157 on an unmerged branch whose
ordinals 156 through 158 were taken on `main` first; refiled as 160 with its
content unchanged except for spec 155 as merged and a Verification block that
fails before the build.

**D-8 (2026-10-10, refile): the page chain is checked structurally, as spec
159 D-4 allows.** Spec 159 as filed corrected its D-4: a continuation token is
integrity checked but not authenticated, so a well-formed token proves nothing
to a third party about which pages a caller fetched. "Broken continuation
chain" in 3.3 is therefore decided from the recorded pages alone: every page
repeats one snapshot, `requestDigest` and `closureDigest`; every page but the
last carries a non-null continuation and the last carries none; and each
page's first member key sorts strictly after the previous page's last member
key under 159's 3.10 order, so no key repeats. A manifest that passes proves a
consistent, terminating, non-overlapping page set. It does not prove that no
member was skipped between pages, which only the consumer that fetched them
can know (159 3.10); the validator MUST NOT claim more.

**D-9 (2026-10-10, refile): the two operations are cataloged.** Spec 162,
filed before this one, holds every CLI invocation form and facade function to
exactly one catalog record (162 R-1). Whichever of 160 and 162 is built second
adds the records for `documentation manifest validate` and `documentation
manifest freshness` and their two facade functions, with effects read from the
code: both read `caller-file` and `source-tree`, `freshness` also reads
`export-directory` for interface exports, neither writes, executes or opens a
connection. The edit to 162's planned files is an `extends` declared by the
build that makes it, not by this filing, because a planned unit cannot be
extended before it exists.
