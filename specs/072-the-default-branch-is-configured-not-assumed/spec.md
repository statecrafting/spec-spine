# 072: The default branch is configured, not assumed

## 1. Purpose

Make the kit protect the branch an adopter actually has.

The `PreToolUse` push gate in `kit/settings.json` compares against the literal
string `main` in four places: the refspec forms it refuses, the test on the
current branch, the test on the trailing positional argument, and the refusal
message. An adopter whose default branch is `master` or `trunk` therefore
installs a gate that refuses nothing it was installed to refuse. Worse than a
gate that fails loudly, it reports success: no diagnostic distinguishes "this
push is safe" from "this gate does not know what it is guarding."

The same assumption reaches past the push gate. The PR gate in the same hook
runs `couple --base origin/main`, which on such a repository names a ref that
does not exist, so the coupling gate fails for a reason that has nothing to do
with coupling. `kit/Makefile` defaults `BASE` to the same ref. `kit/AGENTS.md`,
`kit/.claude/agents/reviewer.md` and six kit skills document commands that
fetch and diff against it. The kit does not have one hardcoded branch name; it
has an unexamined assumption repeated across every layer it ships.

Spec 071 fixed what the push gate refuses and left what it refuses it *on*
alone, recording in its section 4 that the gap is real and needs a
configuration surface whose costs that change should not smuggle in. This spec
is that surface, and the finding behind it is that the surface is smaller than
071 expected: git already knows the answer.

**This spec `amends` 046.** Spec 046 3.4 states the refusal in terms of the
literal name: the gate refuses a push "whose refspec names `main` (`origin
main`, `HEAD:main`, `:main`, `origin +main`)". Section 3.1 below replaces that
name with a value resolved at run time, which is a change to what 046 requires
rather than a correction of code that failed to meet it. Per spec 040 the edge
is declared here only; 046's own `spec.md` is not edited to mention it.

**This spec does not amend 071**, and the distinction is the point of the
edge. Spec 071 3.2 is already written abstractly: "on the default branch, a
push MUST additionally be refused when it would update that branch." It never
requires that the branch be named `main`; its section 4 defers the mechanism
for naming it. Implementing that mechanism satisfies 071's text rather than
contradicting it, so the edges to the units 071 last changed are `extends` with
`nature: superseding`, and no `amends` is owed.

## 3. Behavior

### 3.1 The protected branch is resolved, never assumed

The push gate MUST resolve the protected branch name for the repository the
command acts on, using `git -C "$root"` as the surrounding hook already does
for every other repository fact. The order, highest wins:

1. **`$SPEC_SPINE_DEFAULT_BRANCH`**, when set and non-empty. This mirrors the
   `$SPEC_SPINE_BIN` override the same hook already honours, so the kit gains
   no new convention.
2. **The remote's own HEAD**: `git symbolic-ref --short refs/remotes/origin/HEAD`,
   with the leading remote name and slash stripped. A clone sets this, so for
   most adopters the correct answer arrives with no configuration at all.
3. **`main`**, as a compatibility floor.

Resolution MUST NOT depend on the `spec-spine` binary. The push half of this
hook runs on git alone today, which is why it protects a repository where the
binary is absent or `/setup` has not been run; making the protected branch a
governed read would trade that away for a fact git already holds.

Resolution MUST fall back rather than refuse. A step that cannot answer moves
to the next, and step 3 always answers, so the gate reaches a verdict for every
repository. An adopter whose default branch is `main` MUST see behavior
identical to 071's in every case, including one whose `origin/HEAD` is unset.

### 3.2 Every comparison in the push gate uses the resolved name

The four sites named in section 1 MUST compare against the resolved value:

- the refspec forms (`origin <branch>`, `HEAD:<branch>`, `:<branch>`, and the
  force-with-plus form), which MUST therefore be built from the variable rather
  than written as literal `case` patterns;
- the test on the current branch;
- the test on the trailing positional argument, alongside `HEAD`;
- the refusal message.

The refusal message MUST name the branch it resolved. A gate that says what it
is protecting lets a maintainer tell a correct refusal from a misfire, which is
the property 071 3.2 asked of the message and which matters more once the name
is no longer a constant a reader can assume.

The three-row verdict table of 071 3.2 is otherwise unchanged: fewer than two
positional arguments is refused, `HEAD` or the branch name is refused, anything
else including a version tag is allowed. This spec changes what "the branch
name" denotes, not how the walk decides.

### 3.3 The coupling base follows the resolved branch

The PR gate in the same hook MUST run `couple` against the resolved branch on
the remote it was resolved from, in place of the literal `origin/main`.

`kit/Makefile` MUST derive its `BASE` default the same way, and MUST keep the
`?=` assignment so an explicit `BASE=` on the command line still wins. The
Makefile is a build file rather than a hook, so it MAY compute the value with a
shell assignment rather than repeating the hook's three steps inline.

### 3.4 The documented commands stop naming a branch that may not exist

`kit/AGENTS.md`, `kit/.claude/agents/reviewer.md`, the six kit skills that name
the ref, and this repository's mirrored copies of all of them MUST stop
presenting `origin/main` as the base ref to run against.

Two constraints bound how:

**The commands MUST stay runnable.** These are not illustrations; agents
execute them. A placeholder such as `origin/<default>` would substitute a
broken command for a wrong one.

**Spec 051's subset assertion MUST continue to hold.** `kit_skills.rs` asserts
that each skill's inlined gate floor is a subset of the list in `AGENTS.md`. The
gate chain in `AGENTS.md` contains the base ref, so a change to how that line
is written and a change to every skill that inlines it are one edit, not two.
Landing either alone turns a green test red for a reason unrelated to what it
guards.

### 3.5 The matrix proves it on a repository whose default is not main

`tests/kit_hooks.rs` MUST exercise the shipped `PreToolUse` body against a
throwaway repository whose default branch is **not** `main`, by the same method
071 3.3 established: synthesize a payload, run the body, read the exit code.
The matrix MUST cover, on such a repository:

- a push that would update the resolved branch: refused;
- a tag push made from it: allowed, which is 071's release step preserved;
- a push naming `main`, which on that repository updates an ordinary branch:
  **allowed**, since `main` is not privileged there.

The existing `main` matrix MUST be kept and MUST still pass, which is what
demonstrates that no adopter on `main` regressed. The `$SPEC_SPINE_DEFAULT_BRANCH`
override MUST have a row of its own.

That last row is the one that would have caught this defect: a gate asserted
only against a repository named the way the gate assumes cannot distinguish a
resolved name from a hardcoded one. This is 071 3.3's argument, applied to the
constant 071 left in place.

## 4. Out of scope

**A `spec-spine.toml` key for the branch.** `[coupling] default_branch` is the
obvious governed surface and is deliberately not built here. It would add an
optional key, which is a MINOR bump of `CONFIG_VERSION` to `0.2.0`, and spec
054's `## Verification` block asserts the value `0.1.0` literally, so the config
route drags an amendment to a second spec's acceptance behind it. It would also
put the `spec-spine` binary and `jq` on the push path, which today needs
neither, and force a decision about whether a missing binary degrades the gate
open or closed. None of that buys anything git does not already answer. If an
adopter appears whose `origin/HEAD` is unset and who wants the fact governed
rather than overridden by environment, that is the spec to write, and it can
adopt this resolution as its own last step.

**Giving `couple --base` a default of its own.** The CLI still requires the
flag. Teaching `couple` to resolve a default branch would put a git read inside
a library that spec 000 forbids from shelling out to git, and the flag is
supplied by every caller the kit ships. That is spec 005's territory and a
different argument.

**Remotes not named `origin`.** Resolution reads `refs/remotes/origin/HEAD` and
the coupling base is built on `origin`. Every layer of the kit already assumes
that remote, and generalising it is a wider change than this one.

**A repository with no remote at all.** `git symbolic-ref` fails, step 3
answers `main`, and the gate behaves exactly as it does today. Named so it is
read as the designed path rather than rediscovered as a defect.

**Auditing adopters.** The kit reaches an adopter only by their copying it, so
no change here retrofits an installed harness. Section 5 records what that
costs.

## 5. Resolved decisions

**2026-09-08: `amends` 046, and not 071.** Both specs previously changed this
gate, so the edge was decided by reading what each one's text actually
requires, per the rule 071 5 set. Spec 046 3.4 names the four refspec forms
with `main` spelled out, and this spec replaces that name, so the amendment is
owed. Spec 071 3.2 speaks only of "the default branch" and its section 4 defers
the naming mechanism, so supplying one satisfies it. The lesson worth keeping
is that an amendment is owed by the words, not by which spec touched the file
most recently.

**2026-09-08: git discovery rather than a configuration key.** Spec 071 4
assumed a configuration surface was needed and listed three candidates, each
with costs. The assumption was worth re-testing, and the cheapest candidate
turned out to be one 071 did not list: the remote already records its own
default branch, and `git symbolic-ref` reads it in one call with no parser, no
schema change and no binary. The environment override is kept for the case
where that ref is unset or wrong. Section 4 records what the config key would
have cost and leaves the door open.

**2026-09-08: the floor stays `main` rather than refusing on an unresolved
name.** Refusing would be the safer-looking default and is wrong here: it would
turn an unset `origin/HEAD`, which is common in CI checkouts and bare clones,
into a harness that blocks every push. Falling back to `main` is exactly
today's behavior, so no adopter can regress, and an adopter on another branch
is no worse off than before this spec. The gate is a guard rail, not an
authorization boundary; the branch protection on the forge is the latter.

**2026-09-08: the documentation sweep lands with the executable fix, not after
it.** The two were considered as separate changes. They are not separable:
`AGENTS.md`'s gate chain names the base ref, spec 051's test asserts every
skill's inlined floor against that line, and so a change to one without the
other is a red test. Sequencing them within the change is fine; splitting them
across changes is not.
