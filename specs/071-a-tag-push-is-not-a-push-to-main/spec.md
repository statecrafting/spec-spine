# 071: A tag push is not a push to main

## 1. Purpose

Make the shipped release procedure executable under the shipped harness, and
give the push gate a test that can tell a working gate from a broken one.

The `PreToolUse` hook in `kit/settings.json` refuses a push in two ways: by
matching the refspec against the forms that name the default branch, and by
refusing outright when the current branch is the default branch. Both
over-reach.

**The branch check refuses every push made from the default branch,** not every
push that would update it. `docs/releasing.md` says to tag and push from that
branch right after the release PR merges, so the harness forbids the procedure
the same repository documents. This is not hypothetical: cutting v0.16.0 on
2026-09-08 stalled at exactly this step, and the tag reached the registry only
because a human ran the push by hand. Three of four channels then published.

**The outer match is a substring test over the whole command,** so any command
merely *containing* the text is refused. Authoring this spec tripped it twice:
a scratch script whose test matrix listed the refspec forms was refused while
on a feature branch, because a fixture *describing* the gate contains the
strings the gate matches. A gate that cannot be inspected, tested or documented
from a session it governs is a gate nobody can maintain.

Neither defect was caught, and both shipped to every adopter, because spec 046
gave this gate a **substring assertion** over the hook body. That assertion
passes on the broken body and on the corrected one alike: it tests that a line
exists, not that the gate decides correctly. That is the distinction spec 050
drew for diagnostics and spec 052 for the coupling footer, arriving here.

No new files. Four units, all `extends`-ed:

banner. It is regenerated as part of this change and listed here because the
ledger records what changed, not because it is authored.

**This spec `amends` 046.** Spec 046 3.4 states that the gate refuses a push
whose refspec names the default branch *or* whose current branch is that
branch, flatly. Section 3.2 below contradicts the second clause: on that
branch, only a push with no refspec, or one naming `HEAD` or the branch itself,
is refused. That is a change to what 046 requires, not a correction of code
which failed to meet it, so the edge is `amends` and not mere conformance. Per
spec 040 the edge is declared here only; 046's own `spec.md` is not edited to
mention its successor.

## 3. Behavior

### 3.1 The match is anchored on the command that invokes the push verb

The outer `case` MUST match only a command that *runs* the push verb: at the
start of the command, or immediately after a `&&` or `;` separator. It MUST NOT
match a command that merely contains the text somewhere in an argument, a
heredoc body, or a quoted pattern.

This is the shape the PR gate beside it already uses for `gh pr create`, so the
fix makes the two halves of one hook consistent rather than inventing a
convention.

The refspec check nested inside stays a substring test, and that is correct:
it runs only once the outer match has established that the command really is a
push, and at that point the refspec may appear anywhere in the argument list.

### 3.2 The branch refusal names only what would update the default branch

The refspec refusal is unchanged, and still fires from any branch.

On the default branch, a push MUST additionally be refused when it would update
that branch, and only then. Counting the positional arguments after the verb,
with flags dropped:

- **fewer than two** (a bare push, or a push naming only a remote): no explicit
  refspec, so the push follows the current branch. Refused.
- **two or more** where the refspec is `HEAD` or the branch name: names the
  branch outright. Refused.
- **two or more** naming anything else, a version tag among them: updates no
  branch. **Allowed.**

A tag push carries its own refspec and moves no branch, which is why it belongs
in the last row and why the release runbook can call for it from that branch.

A command chaining **more than one** push MUST be refused on the default
branch, whatever its arguments say. Only the first push is walked argument by
argument, and a walk cannot speak for a push it never examined; refusing is the
conservative reading, and a chained push is not a form anyone needs. Off that
branch the chain is allowed, because the refspec check still sees the whole
command.

The refusal message MUST say what was actually refused, rather than restating
the rule, and MUST name the tag push as allowed, so a maintainer who hits it
can tell a correct refusal from a misfire.

### 3.3 The gate is asserted by running it

`tests/kit_hooks.rs` MUST exercise the shipped `PreToolUse` body as a program:
feed it a synthesized hook payload naming a command and a branch, run it
against a throwaway repository, and read its exit code (2 refused, 0 allowed).
The matrix MUST cover all three rows of 3.2, both defects named in 1, and the
refspec forms that must stay refused.

Where `jq` is absent the guard prints one line saying it skipped, per spec 046
3.5, rather than passing quietly. CI runs this job on `ubuntu-latest`, where
`jq` is present, so the gate is genuinely exercised on every PR.

The text assertions stay, narrowed to the new forms. They are cheap and they
localize a failure to a line; they are simply no longer the only thing standing
between an over-broad match and an adopter.

## 4. Out of scope

**The permission deny list.** The force-push denials live in
`permissions.deny`, a separate mechanism from this hook, and are correct as
they stand. This spec changes only the `PreToolUse` decision.

**Configuring the protected branch.** The gate hardcodes the branch name. An
adopter whose default branch is named otherwise gets no protection, which is a
real gap and a different spec: it needs a configuration surface, and every
candidate (read `spec-spine.toml`, ask `git`, an environment variable) carries
costs this change should not smuggle in.

**Parsing the push command properly.** The positional-argument count is a
heuristic over a shell string, not a command-line parser. It is right for every
form a person or an agent actually writes, and a hook that shelled out to the
network to be exhaustive would tax every Bash invocation. The heuristic's cases
are enumerated in the 3.3 matrix, so its limits are visible rather than assumed.

**Auditing the other hooks for the same shape.** The `PostToolUse` hook matches
on `file_path` values rather than command text, and the PR gate is already
anchored. Only the push gate carried the defect.

## 5. Resolved decisions

**2026-09-08: `amends` 046, rather than treating this as conformance.**
Contrast spec 070, landed the same day, which fixed code that never matched a
sentence its owning spec already contained, and therefore declared no `amends`.
Here spec 046 3.4 says plainly that a push from the default branch is refused,
and the code did precisely that. The spec is what is wrong, so the amendment
edge is the honest record. Making that call by reading the owning spec's actual
words, rather than by how large the code change is, is the rule worth keeping.

**2026-09-08: the anchored outer match is necessary, and still not exact.**
Anchoring stops a command that merely mentions the verb in passing. It does not
stop a command that *contains* a separator followed by the verb somewhere in a
quoted argument, and this spec is its own counterexample: writing this file
with a shell heredoc was refused even after the anchoring landed, because the
verification block below quotes the anchored pattern, and the anchored pattern
contains a separator followed by the verb. A document that describes the gate
accurately matches the gate.

That edge was recorded rather than patched. Escaping it would mean a lexer that
knows which bytes of a command are quoting and which are syntax, which is a
shell parser, and a hook is the wrong place for one. The practical consequence
is small and worth stating plainly: author files that quote these patterns with
an editor rather than a heredoc. The general lesson is 3.3's: a gate matching
shell text will always have edges, so its correctness has to be established by
running it over a matrix of real commands, not by tuning the pattern until the
cases someone thought of stop firing.

**2026-09-08: no `amends` on 029 or 051, checked rather than assumed.** Review
asked whether the specs owning the two edited files also state a contradicted
requirement, which would oblige an `amends` edge to each under spec 040. They
do not, and the check is worth recording so it is not re-litigated. Spec 029
mentions a gate exactly once, and means the coupling gate in the documentation
it ships; it states nothing about what a push gate refuses. Spec 051 3.6
requires that `.claude/settings.json` carry the four hooks `kit/settings.json`
ships and the same `deny` list, and permits divergence only in the permission
`allow` list. This change keeps both files carrying the same four hooks and
leaves `deny` untouched, so 051's requirement is satisfied, not contradicted.
`nature: superseding` on the two `extends` edges records that the content of
those units is replaced; the requirement each owner states is not.

**2026-09-08: a chained second push is refused rather than parsed.** Also from
review, which asked for a comment on the shortest-prefix strip and, in writing
it, exposed that the walk only ever inspects the first push: `git push origin
feat && git push origin HEAD` would have been cleared on the strength of the
first clause. Refusing the chain on the default branch closes it in one line
and costs nothing real, since nobody writes that form deliberately. The
alternative, walking every push in the command, is the shell parser 4 rules
out.

**2026-09-08: the text assertions were kept.** An earlier draft deleted them in
favour of the behavioral matrix. A text assertion that fails tells you which
line went missing, which a behavioral matrix does not, and the two together
cost one test file.

## Verification

Each line below is one command: spec 049 3.2 makes a fence's body line a
command, so no line may depend on a variable another line set.

Every assertion fails against pre-071 code. The executable guard is the one
that matters: run against the shipped body it reports that a tag push from the
default branch was refused when it should have been allowed, which is the
release step this spec restores.

```verify:cli
cargo build --release --locked
# 3.3 the guard that runs the gate against the command matrix.
cargo test -p spec-spine-core --test kit_hooks --locked
# 065's generator keeps the embedded copy in step with the tree.
cargo test -p spec-spine-core --test scaffold --locked
# 3.1 the anchored outer match reaches all three copies.
grep -qF "in 'git push'*|*'&& git push'*" kit/settings.json
grep -qF "in 'git push'*|*'&& git push'*" .claude/settings.json
grep -qF "in 'git push'*|*'&& git push'*" crates/spec-spine-core/src/kit_embedded.rs
# 3.2 the unconditional branch refusal is gone from all three.
! grep -qF '= main ] && blk=1' kit/settings.json
! grep -qF '= main ] && blk=1' .claude/settings.json
! grep -qF '= main ] && blk=1' crates/spec-spine-core/src/kit_embedded.rs
# 3.2 the message names what was refused, and names the allowed tag push.
grep -qF 'this would update main' kit/settings.json
grep -qF 'A tag push such as' kit/settings.json
```
