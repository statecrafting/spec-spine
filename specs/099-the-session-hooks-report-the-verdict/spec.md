# 099: The session hooks report the verdict, not a guess

## 1. Purpose

### 1.1 One hook learned to read the exit code; two did not

Spec 080 found the kit's `PreToolUse` PR gate testing `spec-spine check` as a
boolean and calling every non-zero result "a committed shard tree is stale",
and fixed it: the gate now switches on `0`, `1`, `2`, `3` and anything else,
and says a different true thing for each. The two hooks that report freshness
to the *session* rather than to a pull request were left as they were.

The `Stop` hook still reads:

```sh
"$sc" check >/dev/null 2>&1 && exit 0
echo '[freshness] STALE: run `spec-spine compile` and `index` and commit the regenerated shards with the change that made them stale.'
```

Two decisions are made in those two lines and both are wrong. The output is
discarded, so the verdict the verb reached never reaches the reader; and the
exit code is read as a boolean, so one sentence answers four different
questions.

The `SessionStart` hook does read the output back, which is why spec 075 built
it that way, but it matches a fixed vocabulary that spec 098 has since
extended.

### 1.2 What each hook says today, reproduced

Reproduced on 2026-09-16 with the `0.19.0` in-tree binary against a scratch
corpus created by `spec-spine init`, running the shipped hook bodies out of
`kit/settings.json` verbatim. One spec claims `src/nothing.rs` while declaring
`implementation: complete`; the other rows add a second defect to it.

| Corpus | `check` says | exit | `Stop` hook says | `SessionStart` says |
|---|---|---|---|---|
| A claim that does not resolve | `codebase-index: UNRESOLVED CLAIM: 1 unresolved claim(s) ... which is not staleness` | 2 | `[freshness] STALE: run spec-spine compile and index` | `codebase index: unknown (check exit 2)` |
| That, plus a missing shard | both lines, with `regenerating addresses the stale shard(s) only` | 2 | `[freshness] STALE: run spec-spine compile and index` | `codebase index: STALE, run spec-spine index` |
| A spec whose id disagrees with its directory | `spec-registry: INVALID: the corpus fails validation` | 1 | `[freshness] STALE: run spec-spine compile and index` | registry half correct; index half correct |
| An unknown key in `spec-spine.toml` | `spec-spine: config error: ... unknown field` | 3 | `[freshness] STALE: run spec-spine compile and index` | `unknown (check exit 3)` on both halves |

Every `Stop` cell is the same sentence, and it is false in three of the four
rows and half-true in the fourth. The `SessionStart` mixed row is the one worth
naming separately: the verb printed both halves of its verdict and the hook
relayed the half that regeneration fixes while dropping the half it does not.
A reader who follows that banner regenerates, sees the refusal survive, and has
been told nothing about why.

### 1.3 Why the remedy is the expensive part

`spec-spine compile` and `spec-spine index` write into `.derived/`. Told to run
them against a corpus whose actual defect is a config error or an unresolved
claim, a session regenerates shards that were already correct, commits them,
and arrives at the same refusal with a dirtier diff. Spec 098 §1.2 measured the
same loop at the verb; the `Stop` hook reprints it at the end of every
response, which is where a session decides what to do next.

Spec 098 §3.5 and §3.5.1 deliberately left both hooks alone and filed the
carry-forward as `statecrafting/spec-spine#216` so that the
misleading-remediation problem would not be reported as closed on 098's
strength. This spec is that carry-forward.

### 1.4 What this spec does not decide

Design note 06 §3.9 records open question **H-6**: does the `Stop` hook refuse,
or advise? It advises today, exiting `0` in every branch. This spec keeps that
exactly, in every new branch as well, so H-6 stays open and is decided by a
human rather than by a message fix. Note 06 §5 says the same in the other
direction: the `Stop` hook's remedy line "is filable while every row below
stays open", because a verdict that is wrong is wrong under either answer to
H-6.

## 2. Territory

No new behavior in any crate. The hooks live in three files carrying
byte-identical command bodies:

| Path | Status before this spec |
|---|---|
| `kit/settings.json` | Established by 029, content superseded by 046; extended by 048, 051, 063, 064, 071, 072, 074, 075, 080 |
| `.claude/settings.json` | Established by 051 §3.6, which requires this repository to run the hooks it ships |
| `.codex/hooks.json` | Shipped by 081, **owned by no spec**. Claimed here |

The acceptance lives in `crates/spec-spine-core/tests/kit_hooks.rs` (spec 046's
file). `crates/spec-spine-core/src/kit_embedded.rs` is regenerated from `kit/`
by `scripts/gen-kit-embedded.py`. `spec-spine.toml`'s
`[index] extra_hashed_inputs` gains one glob, for the reason D-2 records.

## 3. Behavior

### 3.1 The `Stop` hook reads the exit code and the report

The `Stop` hook MUST capture `spec-spine check`'s combined output and its exit
status, and MUST branch on the status:

- **`0`**: both trees fresh. The hook prints nothing and exits, as today.
- **`2`**: a refusal the verb described. The hook MUST read the report back
  rather than assume which refusal it is:
  - if the output carries `spec-registry: STALE` or `codebase-index: STALE`,
    the staleness line is printed **unchanged, wording included**, together
    with the existing sentence explaining why the hook does not regenerate;
  - if the output carries `codebase-index: UNRESOLVED CLAIM`, a second line
    MUST say that a spec claims a unit that does not resolve, that this is not
    staleness, that regenerating does not clear it, and where the full list is
    (`spec-spine index diagnostics`);
  - in the **mixed** case both lines MUST be printed, neither elided;
  - if neither token is present, the hook MUST say it received an exit `2` with
    a report it does not recognise, and MUST NOT translate it into either
    remedy.
- **`1`**: the corpus does not validate. The hook MUST say so, MUST NOT call
  the tree stale, and MUST NOT name regeneration.
- **`3`**: the read was not performed. The hook MUST say so in those terms,
  MUST name the binary the resolver chose and what it answers to `--version`
  (spec 080 §3.2), and MUST NOT name regeneration.
- **any other code**: reported verbatim as unrecognised, never as fresh and
  never as stale.

Every branch MUST exit `0`. The hook advises; §1.4 is the whole of the reason.

### 3.2 The binary is asked whether it has the verb, before its code is believed

`clap` spends exit `2` on an unrecognised subcommand and `spec-spine` spends
exit `2` on staleness, so a binary predating `spec-spine check` (every release
before 0.18.0) returns the staleness code without having read anything. Spec
063 §3.1 states the rule and the `SessionStart` hook already follows it.

The `Stop` hook MUST probe `"$sc" check --help` before reading `check`'s exit
code, and when the probe fails MUST report that the binary does not carry the
verb, name what it answers to `--version`, and say that the trees were not
judged. It MUST NOT report staleness in that case.

`--version` MUST NOT be asked on the happy path, for spec 080 §3.2's reason:
the hook runs at the end of every response, and the version read exists to
qualify a non-answer.

### 3.3 The `SessionStart` hook reports the unresolved-claim verdict

The index half of the `SessionStart` banner MUST recognise
`codebase-index: UNRESOLVED CLAIM` and MUST report:

- **stale only**: unchanged, wording included. `STALE, run spec-spine index`.
- **unresolved only**: an unresolved claim, stated as not staleness, with
  regeneration named as something that does not clear it.
- **mixed**: both, with regeneration attributed to the stale half only.
- **fresh**: unchanged.

The `unknown (check exit N)` fallback MUST remain for a report the hook does
not recognise. It is the right answer to an unexpected shape and the wrong
answer to a shape the verb documents.

The registry half is unchanged. Bare `check` cannot emit
`spec-registry: REFUSED`, which spec 077 §3.4 gates behind `--fail-on-warn`,
and a branch for an unreachable line would be untestable decoration.

### 3.4 One change, three copies

`kit/settings.json`, `.claude/settings.json` and `.codex/hooks.json` MUST carry
byte-identical hook command bodies after this change, and a test MUST assert
that for all three. Spec 051 §3.6 already pins the first two;
`.codex/hooks.json` has been the third copy since spec 081 with nothing
comparing it to anything, which is how a copy drifts.

`crates/spec-spine-core/src/kit_embedded.rs` MUST be regenerated by
`scripts/gen-kit-embedded.py` in the same change, so `init --with-kit` writes
the corrected hooks rather than the ones this spec replaces.

### 3.5 The acceptance runs the shipped bodies against a stand-in binary

`kit_hooks.rs` MUST run the **shipped** `Stop` and `SessionStart` bodies, taken
out of `kit/settings.json` rather than restated, against a stand-in binary
whose `check` exit code and output are both chosen by the test (the shape spec
080 §3.4 established for the PR gate). It MUST assert, at minimum:

- exit `2` with an `UNRESOLVED CLAIM` report: the hook names the unresolved
  claim and does **not** print the staleness line or name `spec-spine compile`;
- exit `2` with a `STALE` report: the staleness line is printed with its
  wording intact;
- exit `2` with both: both lines appear;
- exit `1`: the corpus is reported as failing validation, not as stale;
- exit `3`: the read is reported as not performed, with the binary and its
  `--version` answer named, and not as stale;
- a binary whose `check --help` fails: reported as a binary that does not carry
  the verb, not as stale;
- exit `0`: nothing is printed;
- **every** case exits `0`, which is what pins §1.4's posture.

The `SessionStart` assertions MUST cover the four cases in §3.3, including that
the stale-only banner text is unchanged.

## 4. Out of scope

- **H-6, whether the `Stop` hook refuses.** §1.4. The posture is pinned as it
  is and the decision stays with a human.
- **The `PostToolUse` hook.** It pipes `check`'s own output to `tail -6`, so
  spec 098 already corrected what it says. Verified at `56c041c`: it relays the
  verb and translates nothing.
- **The `PreToolUse` PR gate's exit `2`.** It maps exit `2` to staleness
  without spec 063's probe, so a binary predating the verb is refused with a
  staleness message there too. It is spec 080's territory, it refuses in the
  safe direction, and correcting it is a separate change with its own
  adopter-facing message. Named here so the gap is recorded rather than
  rediscovered.
- **`I-004`'s exit code.** Whether an unresolved claim should exit `1` rather
  than `2` is design note 05 §9.4's R-4 and needs an `amends` edge on spec 086
  §3.1. Both hooks here read whatever code the verb spends; neither depends on
  which one it is.
- **Every adopter's own copy.** The release note is the instrument, as it was
  for `kit/Makefile` in spec 089 §4: adopters re-copy `settings.json`.

## 5. Resolved decisions

**D-1 (2026-09-16): the exit `2` branch reads the report rather than splitting
the exit code.** Exit `2` carries three distinguishable verdicts after spec 098
and one code. A hook that guessed from the code alone would have to pick one,
which is the defect being fixed one level down. Reading the attributed prefixes
the verb prints (`spec-registry: STALE`, `codebase-index: STALE`,
`codebase-index: UNRESOLVED CLAIM`) is the same technique the `SessionStart`
hook has used since spec 075 for the same reason: the composed code cannot say
which tree moved, and the report lines can.

**D-2 (2026-09-16): `.codex/hooks.json` is claimed *and* added to
`[index] extra_hashed_inputs`.** This was decided the other way first, on the
argument that §3.4's parity test refuses three-copy drift on every `cargo test`
and so is stronger than making a shard stale, and that `CLAUDE.md` keeps the
hashed-inputs list narrow on purpose. The corpus refused that reasoning
outright: with the claim in place and the glob absent, `lint --fail-on-warn`
exits 1 with

```
L-008 [warning] spec '099-...' claims '.codex/hooks.json', which is in no
content hash: its contents can change without staling any shard.
```

Spec 057 wrote that lint for exactly this shape, and the two properties are not
interchangeable. The parity test answers "do the three copies agree"; the hash
answers "does the ledger know what this file said", which is what spec 023's
attestation signs. A governance file claimed by a spec belongs in the scalar,
which is the criterion `CLAUDE.md` states, and both siblings are already there.
Recorded as a reversal rather than rewritten, because the first argument is one
a reader may well reach again.

**D-2.1 (2026-09-16): the `Stop` hook's "not regenerated here" line moves onto
the staleness branch.** It explains why the hook does not repair a *stale*
tree. Printed under an unresolved claim or a config error it would re-imply
that regeneration was the withheld remedy, which is the thing §3.1 removes.

**D-3 (2026-09-16): the staleness wording is not improved while it is being
kept.** The `Stop` hook's stale line could name which tree moved, the way the
`SessionStart` banner does. It is left exactly as it is: spec 098 §3.3 kept the
stale-only report unchanged so a caller reading staleness today reads it after,
and the same courtesy is owed to an adopter reading this hook's output. The
diff stays about the three cases that were false.
