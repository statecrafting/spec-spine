# 208: The 0.32.0 release moves the package version, the pin and the registry schema together

## 1. Purpose

0.31.0 was published from `bcd91b8f`. `main` has since merged engine changes
that published 0.31.0 does not contain:

- 205 (#507): the YAML reader takes serde-saphyr 2.0.
- 201 (#519): a release ships its attestation bundles, requires signing, and
  verifies what it published.
- 206 (#520): a stopped merge regenerates its derived tree, through the
  `resolve-derived` verb.

`main` has also merged 200 (#502), 202 (#503), 203 (#506) and 204 (#518),
which change the dependency policy records, the CI and release workflows and
`AGENTS.md` and no engine source, and ratified specs 199 to 207.

Every change this release ships is now on `main` under this change. The next
step is the tag, cut at this change's head (3.2).

207 rides with this release rather than ahead of it: `registry list` filters
by implementation state and by whether `verify` would run anything, and the
record gains `declaresAcceptance`. It raises the registry schema to 1.11.0,
and the managed gate runs the exactly pinned released engine (spec 199 3.2),
so a 0.31.0 engine cannot regenerate or judge 207's shards and 207 cannot
pass governance on `main` before 0.32.0 exists (207 D-7). This change is
therefore built on 207's branch, its shards are regenerated at registry
1.11.0 by the 0.32.0 build, and the tagged head contains 207.

Spec 124 3.1 moves `main` to the version the next release is cut at. Spec 199
carries the acceptance for this repository's package identity and its exact
engine pin, both at 0.31.0, and spec 156 3.3 requires a later bump to move the
pin in the same change.

## 2. Territory

The three package manifests and the workspace entries of `Cargo.lock`, the
exact pin in `spec-spine.toml`, the declared pin in
`.statecraft/environment.json`, and the verifier fixtures regenerated by
`generate.py` from the 0.32.0 build. The registry schema constant, its test
literals, the shard schemas and the documentation row are spec 207's
territory and are recorded there. This change adds no engine behavior of its
own.

## 3. Behavior

### 3.1 One version, one pin

`Cargo.toml`, `npm/package.json` and `py/pyproject.toml` carry 0.32.0
(`scripts/bump_version.py --check 0.32.0`). `spec-spine.toml` `[meta]
required_version` is `=0.32.0`, and `.statecraft/environment.json`
`pins.spec_spine` records the same version. The producer pin in that record
names the spec-spine-core that Statecraft itself links, so it does not move
here.

### 3.2 The release precedes the merge

Unchanged from spec 199 3.2: the managed gate installs the exact pinned
release, and a 0.32.0 engine refuses a `=0.31.0` pin, so the release is
tagged at this change's head, published on all four channels, and only then
is this change merged. The tagged tree is the tree that merges, up to commits
that change no engine source or schema; one that does requires a new version
(spec 124 "A version names one behavior").

### 3.3 The registry schema restamp

`REGISTRY_SCHEMA_VERSION` reads `1.11.0` (spec 207 3.3), and the committed
registry is regenerated by the 0.32.0 build. Every registry shard restamps
`specVersion`; a spec whose own `## Verification` section holds a command
also gains `declaresAcceptance`. No `shardHash` moves apart from the specs
this change edits.

### 3.4 Acceptance

Spec 199's complete block is carried. Only the five version literals change:
the four spec 199 3.1 names and the `pins.spec_spine` literal. Spec 207's own
block asserts the registry schema and is not repeated here.

## Decisions

**D-1 (2026-10-27).** The owner directed the 0.32.0 release on 2026-10-27,
carrying spec 207's registry schema 1.11.0, built on 207's branch in one
change, as spec 169 rode spec 195. The owner approved its publication on
2026-10-27: tagged at this change's head once its pull request is open, after
the packaged-producer check and the release sweep pass on that head.

**D-2 (2026-10-27, owner).** 0.32.0 is published: tag `v0.32.0` names
`7d649eb2`, the head of #521, which merged. The owner's rulings of 2026-10-27
move this spec to `implementation: complete` on that evidence and the
`verify 208` run recorded in the pull request, and ratify it.
