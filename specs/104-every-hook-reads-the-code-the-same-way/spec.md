# 104: Every hook reads the exit code the same way

## 1. Purpose

### 1.1 One tool, two meanings, for exit 2

Spec 063 states the rule: establish that the binary understands the verb
**before** reading its exit code. clap spends exit `2` on an unrecognised
subcommand and this tool spends exit `2` on staleness, so a binary predating
`spec-spine check` (every release before 0.18.0) hands back the staleness code
without having read either tree.

The `Stop` and `SessionStart` hooks obey that rule: spec 099 §3.2 put a
`check --help` probe in both. The `PreToolUse` PR gate does not. Its exit-2
branch is:

```
2) { echo "[pr-gate] BLOCKED: a committed shard tree is stale in $root."
     echo '[pr-gate] Run: spec-spine compile and index, whichever tree it named, then commit the shards, push, and retry.'; } >&2
   exit 2 ;;
```

An adopter on 0.17.0 opening a pull request is told a tree is stale, told to
regenerate it, and regenerates shards that were already correct. Spec 099 §4
recorded the gap rather than fixing it: "It is spec 080's territory, it refuses
in the safe direction, and correcting it is a separate change with its own
adopter-facing message." This is that change.

### 1.2 The same unperformed read, diagnosable in one place and not the other

Reproduced 2026-09-16 with the 0.19.0 binary, on a corpus whose
`spec-spine.toml` carries an unknown key, which the config parser refuses
before any corpus is read:

| Hook | What it says at exit 3 |
|---|---|
| `Stop` | `[freshness] NOT READ: ... the binary at <path> ... It answers: spec-spine 0.19.0 ...` |
| `SessionStart` | `spec registry: unknown (check exit 3); codebase index: unknown (check exit 3)` |
| `PreToolUse` PR gate | `BLOCKED: the freshness read was not performed ... The binary is <path>, which answers: ...` |

Two of the three name the binary and what it answers, which is what separates
"this binary is too old" from "this config is broken". The banner a session
opens with does not, and that is the one place the information changes what the
session does next.

Spec 099 §3.3 already draws the line this spec applies: the `unknown (check
exit N)` fallback "is the right answer to an unexpected shape and the wrong
answer to a shape the verb documents". Exit 3 is a shape the verb documents.
This spec does not weaken the fallback; it stops exit 3 falling into it.

### 1.3 Why the probe costs nothing

Spec 080 §3.2 forbids the gate running `--version` on the happy path, for a
good reason: the gate runs on every `gh pr create` and exit `0` is an answer.
That reasoning survives intact here, because the probe is only needed on the
**one code that is ambiguous**. Exit 0, 1 and 3 each mean one thing from any
binary. Exit 2 means two things, so exit 2 is where the gate asks.

This is a refinement of spec 099's shape rather than a copy of it: the session
hooks probe unconditionally, which costs a subprocess per response and per
session start. The gate probes only when it is about to say "stale", so the
happy path is unchanged.

## 3. Behavior

### 3.1 The PR gate probes before it says "stale"

On exit `2` and **only** on exit `2`, the `PreToolUse` gate MUST run
`"$sc" check --help` before printing a verdict.

- The probe succeeds: the binary carries the verb, so exit 2 is this tool's
  staleness code. The message is unchanged, wording included.
- The probe fails: the binary does not carry the verb, so it never read either
  tree and exit 2 came from clap. The gate MUST say that the read was not
  performed, MUST name the binary and what it answers to `--version`, and MUST
  name the 0.18.0 floor, matching what §3.1's exit-3 branch already says. It
  MUST NOT call the tree stale and MUST NOT name `compile` or `index`.

Both outcomes still refuse with exit 2 at the hook level. What changes is which
of two facts the operator is told.

This replaces spec 080 §3.1's exit-2 bullet. Under spec 040 the replacement
text lives here, and 080 is not edited. Where 080 reads:

> - **`2`**: stale. The message stays what it is: which tree, and that the
>   remedy is `compile` or `index` followed by a commit.

it now reads:

> - **`2`**: ambiguous until the binary is asked. `check --help` decides it. If
>   the binary carries the verb, the code is staleness and the message stays
>   what it is: which tree, and that the remedy is `compile` or `index`
>   followed by a commit. If it does not, clap spent the code on an unknown
>   subcommand, nothing was read, and the message is the exit-3 message.

and where 080 §3.2 reads:

> Exit `0` and exit `2` are answers; the version read exists to qualify a
> non-answer, and the gate runs on every `gh pr create`.

it now reads:

> Exit `0` is an answer. Exit `2` is two answers until `check --help`
> separates them, and the version read follows the probe that says it is
> needed. The gate still runs no subprocess beyond `check` itself on the happy
> path, which is what this clause protects.

The rest of spec 080 §3.1 and §3.2 stands: the exit-1, exit-3 and unrecognised
branches, and the rule that every non-zero code refuses, are unchanged.

### 3.2 `SessionStart` reports an unperformed read as one

The `SessionStart` banner MUST, on exit `3`, report both halves as a read that
was not performed, name the binary the resolver chose and what it answers to
`--version`, and not present the result as an unknown shape.

The `unknown (check exit N)` fallback MUST remain for every code the hook does
not recognise, which is spec 099 §3.3's rule and the reason this clause names
exit 3 specifically rather than removing the fallback.

### 3.3 One change, three copies, one acceptance

`kit/settings.json`, `.claude/settings.json` and `.codex/hooks.json` MUST carry
byte-identical hook command bodies after this change, and the test spec 099
§3.4 added MUST keep asserting it. `kit_embedded.rs` MUST be regenerated by
`scripts/gen-kit-embedded.py` in the same change.

`crates/spec-spine-core/tests/kit_hooks.rs` MUST run the **shipped** bodies
against a stand-in binary whose `check` exit code, `check --help` exit code and
output the test chooses, and MUST assert:

- PR gate, exit 2 with a working `check --help`: the staleness message,
  unchanged;
- PR gate, exit 2 with a failing `check --help`: the not-read message, naming
  the binary and the floor, and **not** naming `compile` or `index`;
- PR gate, exit 0 with a failing `check --help`: no probe changes the verdict
  and the gate proceeds, which pins §1.3's claim that the happy path is
  untouched;
- `SessionStart`, exit 3: both halves report a read that was not performed and
  name the binary, and neither says `unknown`;
- `SessionStart`, an unrecognised code: still `unknown (check exit N)`.

## 4. Out of scope

- **H-6, whether the `Stop` hook refuses.** Unchanged, as spec 099 §1.4 left
  it. Every branch here still exits 0 for the session hooks and still refuses
  for the gate.
- **The PR gate's `git diff --quiet -- .derived/` test.** It asks about
  unstaged tracked changes, so a staged shard and an untracked new shard both
  pass it. Design note 06 §3.9 records it; it is a different question from
  which code means what, and it is unfiled. Named here so it is not mistaken
  for something this spec closed.
- **Missing `jq` yielding "skipped" and success.** Note 06 §3.9's fifth row.
  Advisory and enforcing behavior share one exit path; that is a posture
  question, like H-6.
- **Every adopter's own copy.** The release note is the instrument, as in specs
  089 and 099: adopters re-copy `settings.json`.

## 5. Resolved decisions

D-1 (2026-09-16, why the gate probes conditionally where the session hooks
probe unconditionally). §1.3. The session hooks run once per response and once
per session and read every code through one path, so an unconditional probe is
simpler there and its cost is amortised. The gate runs on a user action, spec
080 §3.2 deliberately protects its happy path, and only one of its four codes
is ambiguous. Both shapes obey spec 063; they differ in where the ambiguity is.

D-2 (2026-09-16, why `check --help` rather than `--version` for the probe).
`--version` answers on every binary ever released, which is what makes it safe,
and exactly what makes it useless as a probe: it cannot say whether the verb
exists. `check --help` fails precisely when the subcommand is unknown. The
version read still happens, after the probe, to name what the binary is.

D-3 (2026-09-16, why the gate keeps exiting 2 in both outcomes). The hook's
exit code is a refusal signal to the tool runner, not a relay of the verb's
code. Spec 080 already maps all four verb codes onto hook exit 2 and the
reasoning is unchanged: a gate whose check did not run is not green.
