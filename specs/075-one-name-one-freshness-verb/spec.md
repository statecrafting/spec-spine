# 075: One name for the protocol, one verb for freshness

## 1. Purpose

Make the session protocol unambiguous where it currently collides with the
platform it runs on and with the tool it drives.

**The name.** The kit's entry point is `/init`. Claude Code ships its own
`/init`, which generates a CLAUDE.md: a one-time, repository-level operation
that writes. The kit's is per-session and, in its own words, "reports, it does
not mutate." So the kit shadows a built-in, takes it away from adopters, and
assigns the token the opposite meaning on both axes that matter, frequency and
effect. `spec-spine init` is a third meaning again, and it is the one that is
correct: `git init`, `cargo init` and `npm init` all mean "create a new one of
these, here." The verb is right and the skill is wrong.

**The verb.** Freshness is asked two ways. `spec-spine compile --check` is a
flag; `spec-spine index check` is a subcommand. They answer one question about
two trees, and every consumer has to know both spellings: `AGENTS.md` step 1,
the `SessionStart` hook, the `/init` skill, `kit/Makefile`, `kit/govern.yml`
and CI. The concrete harm this asymmetry did has already been retired, since
spec 063 gave usage errors their own exit code and spec 062 plus
`deny_unknown_fields` make a stale binary announce itself as exit 3. What
remains is not a trap; it is that the protocol has to know two things to ask
one question.

This spec does not fix that by renaming a primitive. It adds a verb above them.

## 2. Territory

The implementation adds one file, `crates/spec-spine-cli/src/cmd_check.rs`,
following the CLI's one module per subcommand convention. Everything else is
`extends`-ed.

**That file is deliberately not in an `establishes` list yet.** This repository
opted into spec 050's `index check --fail-on-unresolved`, and CI runs it, so a
claim on a path that does not exist refuses the gate: spec 044's in-flight
window makes the unresolved unit a `W-001` warning rather than an error, and
this repository's gate refuses warnings too. The claim therefore lands in the
implementing change, with the file, which is exactly the edit
`.claude/rules/adversarial-prompt-refusal.md` names as always legitimate for
the spec being implemented. Filing it in the draft would put the corpus in a
state its own CI refuses, for the sake of claiming a file nobody has written.

**No `amends` is owed, checked rather than assumed.** Three specs looked like
candidates:

- **031** describes the `/init` protocol as a consumer of its stale report, and
  makes that report's *structure* contractual: "each stale shard occupies its
  own stderr line and carries its drift class." It does not require the
  protocol to invoke `compile --check`. Section 3.4 below requires the composed
  verb to pass each tree's report through unchanged, so 031's contract is
  satisfied rather than contradicted. Reformatting those lines would have
  required the amendment; passing them through does not.
- **004** owns `index check`, which this spec does not touch.
- **029** owns `AGENTS.md` and mandates no particular verb in it.

**The exit-code precedence in 3.3 is new behavior, stated by no existing
spec.** Recorded here so a later amends audit does not reopen it. The exit
codes themselves are a stable contract, mapped in one place, and 031 and 004
each fix what their own verb returns; neither says anything about how two
verdicts combine, because until this spec nothing combined them. New behavior
on a new verb owes no amendment to the specs whose verbs it calls. The verb's
own file is claimed in the implementing change, for the reason given above, so
the ownership record for 3.3 arrives with the code that implements it.

**This spec lands after 074**, which is why 074 is a dependency rather than a
sibling. Both edit `AGENTS.md`'s step 1 list and both edit the session skill:
074 schedules the `--version` read and removes the retired stderr rule, and
this spec renames the skill's directory and changes which verbs step 1 calls.
Sequencing them is a textual necessity, not a logical one.

## 3. Behavior

### 3.1 The session skill is `/prime`, with no alias

The skill MUST be renamed from `init` to `prime` in both skill trees, and every
reference to it MUST move with it: `AGENTS.md`'s New Sessions section, the
kit's copy, and the generated `kit_embedded.rs`.

The summary block MUST change with the name. `## initialized: <project>`
becomes `## primed: <project>`, because the header re-encodes the same word and
the contract for that block lives in `AGENTS.md`, which is being edited anyway.

There MUST NOT be an `/init` alias. An alias keeps shadowing the built-in for
the whole deprecation window, which is the defect being fixed, and it buys
nothing: skills are copied files, so an adopter who does not refresh keeps
their old copy regardless, and one who refreshes takes the rename.

The `## New Sessions` heading MUST NOT change. The dispatcher reads that
section by heading, so the heading is the actual cross-agent contract and it is
already neutral.

**The migration note MUST name the failure mode**: an adopter who refreshes the
skills but keeps a customized `AGENTS.md` gets "skill not found", which is loud
and instantly diagnosable rather than silent. That is the whole cost of
skipping the alias and it should be written down rather than discovered.

### 3.2 `spec-spine check` answers the freshness question once

A new top-level verb, `spec-spine check`, MUST run both freshness reads and
report both verdicts.

It MUST be **additive**. `compile --check` and `index check` keep their flags,
their output contracts and their tests, unchanged. A caller that regenerated
only one tree, which CI does, MUST still be able to ask about that tree alone.

It MUST **never write**, carrying the same contract as `--check`: a verb the
protocol calls to read the committed state cannot repair that state as a side
effect of reading it, which is the rule `AGENTS.md` states and the reason the
protocol never substitutes a bare `compile`.

It MUST accept `--fail-on-unresolved` and forward it to the index half.
Without that the composite gate cannot adopt the verb, since the gate chain
runs `index check --fail-on-unresolved`, and a verb the gate cannot call would
leave the protocol still spelling the primitive.

The composition SHOULD live in the library as an additive facade function
(`check_json`), beside the two that already exist
(`check_registry_freshness_json` and `check_freshness_json`), so a binding gets
the composed verdict rather than reimplementing the exit-code fold.

### 3.3 One exit code, composed in a pinned order

The verb's exit code MUST be the most severe of the two reads, in this order:

**`3` dominates `1` dominates `2` dominates `0`.**

- `3` (I/O, parse, schema, config) dominates because a read that could not be
  performed has not answered, and no verdict from the other tree makes the
  overall answer trustworthy.
- `1` (validation failed) dominates `2` (stale) because staleness is not
  meaningful against a corpus that does not validate. `AGENTS.md` already draws
  this conclusion for the reporting case, requiring lifecycle counts to be
  reported as unverified when validation fails; the exit code now agrees with
  it.

The order MUST be pinned by test, not merely documented, because it is the one
part of this verb a caller cannot observe from a single run.

Per spec 037 the verb MUST take `--json` and emit the canonical envelope, with
`verb: "check"` and a `report` carrying both trees' verdicts. The flag MUST
change what is written and never what is decided: the exit code MUST be
identical with and without it.

### 3.4 Each tree's report passes through unchanged

The stale report of each half MUST reach stderr with its structure intact and
attributed to its tree, so a consumer can still read which shards drifted and
in which ledger.

This is not a new requirement. Spec 031 section 3.3 makes the registry stale
report's structure contractual precisely because the session protocol reads
the drifted shard names back to the operator, and exit 2 alone cannot say which
shard moved. A composed verb that summarized or interleaved the two reports
would break a contract that already exists, which is why this section exists
and why no amendment to 031 is owed.

The summary block MUST still be able to report the two trees separately, as it
does today.

### 3.5 Every consumer calls the composed verb

`AGENTS.md`'s step 1, the `SessionStart` hook in both settings files,
`kit/Makefile`, `kit/govern.yml` and the skills' inlined gate floors MUST call
`spec-spine check` and MUST NOT name either primitive.

Spec 051's subset assertion MUST continue to hold: `kit_skills.rs` asserts each
skill's inlined floor is a subset of `AGENTS.md`'s list, so the gate list and
every skill that inlines it change together or the test goes red.

The two primitives remain documented as the single-tree reads, in
`docs/adoption-guide.md` and the README's capability table. Removing them from
the protocol is not deprecating them.

## 4. Out of scope

**Regrouping `attest` and `verify-attestation`.** These are two top-level verbs
where every other noun groups its operations, and the obvious fix,
`attest create` / `attest verify`, is refused here for a specific reason:
`spec-spine verify <id>` already exists and means "run a spec's acceptance
block." `attest verify` would put a second `verify` in the surface with a
different meaning, one bare and one under a noun, which is the same shape of
collision this spec exists to remove from the skill namespace. Introducing one
while fixing another would be a poor trade. The current name is ungainly and
unambiguous, which is the right way round.

If the surface is ever regrouped it belongs in a single 1.0 surface-freeze
spec that batches every rename into one deprecation window with
`[meta] required_version` doing the enforcement, rather than paying a per-verb
migration tax three times in 0.x. That spec, when written, MUST pick a name
that avoids the `verify` collision: `attest check`, or `attestation verify`
with `attest` becoming `attestation create`.

**Deprecating `compile --check`.** Removing it would break `govern.yml` in
every adopter for a cosmetic gain, and the harm that once justified touching it
is retired. Section 3.2 is additive by design.

**Making `check` run the whole gate.** It answers freshness only. `lint` is
conformance, `coverage` is ownership, and `couple` needs a base and a head, so
a verb that ran all of them would be the Makefile with a different name. The
composite gate is spec 064's, and it remains the place where the whole chain is
defined once.

**A `check` that also writes.** Explicitly refused in 3.2 and named here so it
is not proposed as a convenience later: the moment the protocol's read verb can
repair the tree, a stale committed ledger stops being visible as a defect on
the branch, which is exactly how the 017/021 drift reached main.

## 5. Resolved decisions

**2026-09-08: a verb above the primitives, not a rename of one.** Three shapes
were considered. Adding `compile check` as a subcommand alongside `--check` is
additive but leaves two spellings of one primitive forever, and the protocol
still calls two verbs, so it fixes the shape and not the duplication.
Deprecating `--check` breaks every adopter's CI for a cosmetic gain. Composing
a new verb is the only option where the number of things the protocol has to
know goes **down**, and it is additive, so it is the one that ships.

**2026-09-08: `/prime` rather than `/orient`.** `/orient` describes the agent's
posture rather than an operation on the session, and gives the summary block an
awkward header. `/prime` names what is done to the session, has prior art for
exactly this pattern, and yields `## primed:` as a state the block can report.
`/status`, `/context` and `/doctor` are all Claude Code built-ins and therefore
unavailable, which is the constraint that eliminated the otherwise ideal
`/doctor` ("check, never fix").

**2026-09-08: no amendment to 031, because pass-through preserves its
contract.** The composed verb was initially assumed to amend whichever spec
owned the protocol's gate list. Reading 031 showed it constrains the *shape of
the stale report*, not the identity of the caller, so 3.4 satisfies it. This is
the third time in three specs that reading the owning spec's actual words
produced a different edge than the size of the change suggested.

**2026-09-08: `attest` keeps its ugly name.** Recorded as a decision rather
than an omission, because the grouping is the obvious tidy-up and someone will
propose it again. The reason it is refused is written in section 4 so the next
proposal starts from the `verify` collision rather than rediscovering it.

**2026-09-08: `check` returns `1` for a refused unresolved-unit diagnostic as
well as for a validation failure, and the report lines are what separate
them.** Section 3.3 pins the precedence over four codes and does not say that
one code can arrive from two conditions, but it does require
`--fail-on-unresolved` to be forwarded, and spec 050 already spends `1` on that
refusal. So `1` is genuinely ambiguous on this verb where it was not on either
primitive. Rather than invent a fifth code, which would break the stable
exit-code contract, both `AGENTS.md` copies now tell the reader to read the two
report lines under the code. The lines say which tree and which condition; the
code says only how severe.

**2026-09-08: the composed verb compiles once, not twice.** The facade route
(`check_registry_freshness_json` then `check_freshness_json`) would have been
three lines, and it compiles the corpus twice. This verb exists to make one
question cost one ask, so `check_report` takes the typed path the CLI already
uses: `compile` once, then `compare_committed_registry`.

**2026-09-08: a corpus that fails validation reports `fresh: false` with
staleness uncomputed, rather than guessing.** Staleness is not meaningful
against a corpus that does not validate, which is exactly why `1` outranks `2`
in the fold, so the registry half does not compute it and says so through
`validationPassed: false`. A `fresh` member that was absent instead would have
made the payload shape depend on the verdict, which no other verdict verb does.

**2026-09-08: the gate list's order moved so the two lists stay walkable.**
`kit_gate.rs` (spec 064) walks `kit/Makefile`'s gate against `AGENTS.md`'s list
in order, and the Makefile's read-only gate leads with the freshness read where
`AGENTS.md` had `lint` before `index check`. `check --fail-on-unresolved` is
therefore listed immediately after the two writing verbs, which is also the
order the sentence above the fence already describes ("`compile` and `index`
write; the checks follow").

**2026-09-08: the hooks read the composed verb's report lines rather than its
exit code.** One code cannot say which tree moved, and the `SessionStart` hook
reports both trees by name. It therefore captures stdout and matches on
`spec-registry:` and `codebase-index:`, which is the pass-through 3.4 exists to
guarantee, used for the purpose 3.4 names.

**2026-09-08: two hook message strings were reworded around a test's scanner,
and that is recorded rather than hidden.** `kit_hooks.rs`'s write-scanner reads
`spec-spine <word>` out of a hook body and resets its look-behind after each
match, so a prose line naming the binary twice, or naming it inside backticks,
is read as an invocation. Two new messages tripped it. The messages were
reworded (one names the verb without the binary, one names `compile and index`
once); the scanner was left alone, because loosening a guard that refuses
writing verbs in hooks to accommodate prose is the wrong direction, and spec
046 exists because three hooks wrote when they should have read.
