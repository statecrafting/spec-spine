## 7. Genuinely new contradictions

Five, each found by doing the work rather than by reading. **[corrected]** All
five were re-examined by the second session; one is fixed, three were
overstated, and the corrections are inline below. Note 11 §4 carries the
measurements.

1. **`make gate` judges with whatever binary is on `PATH`.** `SPEC_SPINE ?=
   spec-spine` resolves to `~/.cargo/bin/spec-spine 0.20.0` on this machine,
   three releases behind the checkout, while the Makefile's own header
   documents a resolution order preferring `./target/release`. Caught when a
   built lint exemption still reported ten warnings through `make` and none
   through the in-tree binary. Every gate in §4 was re-run with the override
   and no verdict changed, so nothing here rests on it, but a session that
   never noticed would have been gating with a stale binary all day. The
   Makefile is spec 092's territory; **not fixed**, because fixing it under
   cover of another spec's build is the scope creep the corpus refuses.

   **[corrected] Fixed, as spec 117**, on its own branch and under its own
   evidence, which is the door this paragraph said was the right one. The
   territory attribution above is also imprecise: `index owner Makefile`
   reports `094-one-gate-and-the-boundaries-it-holds` as the **establisher**
   and 092 as an `extends`, so 117's edge names 094. Spec 117 also refuses an
   unusable explicit override instead of silently substituting one, and
   announces the resolved binary and its version before the chain runs.

2. **A MINOR-ahead attestation does not verify.** Spec 103's draft asserted it
   must, reasoning that a MINOR is additive. The MAJOR gate does admit it and
   `verify_recompute` then compares `schemaVersion` like every other field, on
   purpose (spec 068 §3.3), so the result is a content mismatch. Two layers
   disagree about what a MINOR means. The fixture records the measured
   behavior and spec 103 §3.5 names the disagreement; **whether the recompute
   should skip the field is undecided** and is a real question for whoever
   owns attestation compatibility.

   **[corrected] "Two layers disagree" overstates it, and the question is not
   open.** Four separable layers were measured (note 11 §4.2), and each one
   does exactly what its owning spec promises:

   | layer | on a MINOR-ahead payload | promised by |
   |---|---|---|
   | schema admissibility (MAJOR gate) | admits | spec 068 §3.3; `docs/schema-versioning.md` |
   | strict payload validation | **refuses** a real MINOR-ahead payload, because every attestation DTO is `deny_unknown_fields` and a MINOR adds a field | spec 068 §3.5 |
   | digest integrity over the attested territory | intact: every unit content hash matches | spec 021 |
   | recomputation equality | mismatch on `schemaVersion` alone | spec 068 §3.3, explicitly |

   No normative contract conflicts with another, so **no compatibility
   amendment is proposed**. What a "MINOR-ahead payload that verifies" would
   need is for the recompute to drop `schemaVersion` from the comparison, and
   spec 068 §3.3 requires the opposite by name, for the reason spec 103 §3.5
   records: skipping it lets an attestation claiming a schema this build never
   emitted recompute as a match. Dropping a field from an integrity comparison
   to obtain a match is the failure, not the fix. Spec 103's fixture keeps the
   measured outcome, which is correct.

3. **The facade's configuration argument is snake_case while every emitted DTO
   is camelCase.** A consumer that assumes one casing gets a config error at
   exit 3 on its first call. Asserted rather than changed (spec 104 §3.3):
   `Config` is the TOML model and renaming the boundary breaks a type another
   spec owns. Statecraft should be told.

   **[corrected] The shape, stated exactly**, because "the configuration
   argument" understates which surface it is: **every** facade entry point
   takes the configuration as its own `config_json` string argument, and that
   string is the `spec-spine.toml` model — table names and keys spelled as in
   the TOML, no `rename_all`. Every other facade request object and every
   emitted DTO is camelCase. All of them carry `deny_unknown_fields`, so the
   mistake is a loud refusal and never a silent default. The contract test is
   retained and runs against the packaged crate on every release pre-flight
   (`scripts/verify-packaged-producer.sh`, "a camelCase config key is refused,
   not silently ignored"). No rename and no alias: either would be a breaking
   change to a type specs 000 and 001 own and would need its own compatibility
   spec.

4. **`couple`'s freshness guard fires before the gate for an unwithdrawn
   working-tree deletion.** Deleting a file a unit claim still names makes the
   working tree's index unresolved, so `couple` exits 2 on staleness before
   any ownership question is asked. Pre-existing spec 005 / 023 behavior, not
   introduced by spec 100, and it means one shape of the add-then-delete case
   is unreachable through the CLI. Recorded as spec 100 D-9.

   **[corrected] The refusal is not freshness, and it is already tracked.**
   Reproduced on the candidate by deleting
   `crates/spec-spine-core/src/coverage.rs` in the working tree (note 11
   §4.3). `check` gets it right: **exit 1**, seven `I-004` unresolved claims,
   and the message says in as many words "which is not staleness". `couple`
   refuses the same state at **exit 2** through the shared `Error::Stale`,
   whose `Display` reads "index is stale" and whose per-shard reason is
   `blocking-diagnostics`. So: the condition is **unresolved ownership**, a
   validation failure; the exit code and the label are freshness's. That is
   the gap spec 079 §6 already tracks under "`Error::Stale`'s wording at the
   freshness guard", and spec 079 D-4 records why it was left out of scope
   (the shared error variant, and a tier-1 claimed file). It attributes to
   specs 005/023 what is spec 079's known limitation.

   The distinction that matters is preserved and must stay preserved: this is
   a **precondition refusal**, not a coupling verdict. `C-001` and `C-002`
   never ran. Nothing here is a reason to relax a validation in order to reach
   the later gate.

5. **A `.crate` digest is a function of the commit, not of the crate's
   sources.** `cargo package` embeds the git sha in `.cargo_vcs_info.json`, so
   a documentation-only commit moves the digest with byte-identical crate
   sources. It is fine as "was this cut from that commit" and useless as "did
   the library change", and any process that records one has to re-cut it at
   the published revision.

   **[corrected] It is a function of both.** The `.crate` digest is the
   SHA-256 of the whole archive: the crate's sources **and** the generated
   metadata (`Cargo.toml`, `Cargo.toml.orig`, `.cargo_vcs_info.json`, and a
   `Cargo.lock` for the binary crate). The original observation — that a
   commit alone moves it — is right; the generalisation is not, and "not of
   the crate's sources" is false. Measured by cutting all three crates at two
   commits (note 11 §4.4): `spec-spine-types` moved its archive digest with
   byte-identical contents, `spec-spine-core` moved both because a packaged
   test file was added, and `spec-spine-cli` moved both because its packaged
   `Cargo.lock` pins the two sibling archives' checksums. That last one has a
   release consequence: all three archives must be cut from the one revision
   that is actually published.
